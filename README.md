# CashGuard — нарушения кассовой дисциплины по видео

> **Назначение:** точка входа для жюри и проверяющих по ТЗ, раздел 8: адреса, ключ, запуск, архитектура, модели, типы нарушений, нормы и ограничения.
> **Владелец:** S0 (интегратор) · **Статус:** финальная версия к сдаче, 18.10.2026. Описывает то, что реально работает в сервисе; целевая архитектура из `docs/` реализована не полностью (см. «Что сделано и что нет»).

CashGuard — локальный AI-сервис для ForteBank Datathon 26. Пользователь загружает видеозапись кассы (`.mov` или `.mp4`). Сервис:
- отвечает, есть ли видимые признаки возможного нарушения (`violation` или `no_violation`);
- для каждого нарушения показывает тип, таймкод, 1–3 кадра-доказательства и описание того, что видно;
- указывает правило и нормативный акт Республики Казахстан (название, пункт).

Все модели работают на нашем Mac. Облачные AI-сервисы не используются. Результат — подсказка для проверки человеком, а не юридическое или дисциплинарное заключение (ТЗ, раздел 7).

## Проверка через API (ТЗ, раздел 10)

Загрузка видео:

```bash
curl -X POST <URL>/api/v1/analyze \
     -H "X-API-Key: <API_KEY>" -F "file=@video_017.mov"
# → {"job_id": "<32 hex-символа>"}
```

Статус и результат (опрашивать, пока `status` не станет `done` или `failed`, например раз в 3 с):

```bash
curl <URL>/api/v1/jobs/<job_id> -H "X-API-Key: <API_KEY>"
```

| `status` | Ответ |
|---|---|
| `processing` | `{"job_id": "...", "status": "processing", "verdict": null, "violations": []}` |
| `done` | ровно поля из ТЗ §10: `verdict` = `violation` или `no_violation`; `violations[]` с `type`, `timecode_sec`, `description`, `evidence_frames` (1–3 JPEG в base64) |
| `failed` | `{"job_id": "...", "status": "failed", "verdict": null, "violations": []}` — файл не читается как видео или анализ упал |

Пример ответа `done`:

```json
{
  "job_id": "<job_id>",
  "status": "done",
  "verdict": "violation",
  "violations": [
    {
      "type": "Ценности оставлены без присмотра при уходе",
      "timecode_sec": 18.0,
      "description": "<что видно на кадре>. Основание: <пункт, акт>.",
      "evidence_frames": [{ "timestamp_sec": 18.0, "image_base64": "/9j/..." }]
    }
  ]
}
```

Гарантии ответа:
- в ответе нет полей сверх ТЗ §10 (схема заморожена: [jury_job.schema.json](src/cashguard/contracts/schemas/jury_job.schema.json)); нарушений не больше 5;
- `evidence_frames[0].timestamp_sec` совпадает с `timecode_sec`; `image_base64` — JPEG без префикса `data:`; таймкоды берутся из PTS кадров;
- повторная загрузка того же файла отвечает из кэша (по sha256 файла, версии пайплайна и конфигурации).

| Код | Когда |
|---|---|
| 401 | нет ключа или ключ неверный |
| 404 | неизвестный или некорректный `job_id` |
| 413 | файл больше 100 МБ |
| 415 | не QuickTime/MP4 или контейнер не читается |
| 422 | нет поля `file` |
| 507 | на сервере мало места на диске |

## Веб-интерфейс

1. Откройте адрес из таблицы выше и перетащите видео `.mov` или `.mp4` до 100 МБ.
2. Видны этапы обработки; итог — «Нарушение не обнаружено» или «Обнаружены признаки возможных нарушений».
3. В карточке нарушения — тип, таймкод, описание, норма и кадры-доказательства. Маркеры на шкале видео переводят плеер к событию.
4. Страница «Типы нарушений и нормы» — `<URL>/?view=types`.

Подробно: [docs/ui.md](docs/ui.md).

## Что проверяет сервис сейчас

В боевой конфигурации оцениваются **3 типа нарушений** из каталога (`temporal_rules.codes`):

| Код | Тип для жюри (`type`) | Когда срабатывает | Норма |
|---|---|---|---|
| `VALUABLES_LEFT` | Ценности оставлены без присмотра при уходе | на столе деньги, кассир вышел через дверь или край кадра, и до конца ролика в комнате никого | ПКО п. 20 ч. 2, п. 22, п. 80 (прямая) |
| `THIRD_PERSON_DURING_SERVICE` | Постороннее лицо / второй клиент во время операции | у стола ≥ 2 не-кассиров не меньше 2 с во время обслуживания; место кассира, дубли рамок и мелкие рамки за стеклом двери исключены | ПОП п. 8, п. 16 пп. 1) (косвенная) |
| `SAFE_OPEN` | Сейф оставлен открытым | логика есть, но детектор почти не выдаёт класс `safe_open` (обучен на 2 кадрах), поэтому на практике не срабатывает | ПКО п. 20 ч. 2 (косвенная) |

Остальные типы каталога (всего 26 кодов, [docs/violation_catalog.md](docs/violation_catalog.md)) показаны в интерфейсе, но **не оцениваются**. Если по трём правилам кандидатов нет, сервис отвечает `no_violation`; основание пишется во внутренний `technical_scope.json` задания (`clean_verdict_basis`). Если кассовый стол не найден (другая сцена), ответ тоже `no_violation` с причиной `scene_not_recognized`, а не ошибка: контракт жюри допускает только два вердикта.

## Результаты на 40 роликах организаторов

Прогон 18.10.2026: правила на сохранённых наблюдениях всех 40 роликов (`offline_eval.py`) и сквозной прогон через публичный API (39 роликов).

| Метрика | Значение |
|---|---|
| Верные срабатывания | 3 из 20 роликов с нарушением: Х-26 (18,0 с; разметка 9 с), Х-18 (17,0 с; разметка 20 с), Х-30 (13,0 с, совпадает с разметкой; наш тип «второй клиент», в разметке «посторонний») |
| Ложные срабатывания | 0 из 20 чистых роликов |
| Пропуски | 17 из 20 роликов с нарушением |
| Время через API | медиана 18,1 с, максимум 105,4 с (ролик 142 с), включая очередь; лимит 300 с не превышен ни разу |

Сервис настроен на точность: лучше пропустить нарушение, чем выдать ложное. Причины пропусков:
- Х-20 (сейф открыт): детектор на всех кадрах видит `safe_closed` с уверенностью ≥ 0,95; `safe_open` обучен на 2 кадрах (AP50 0,08). Нужны данные, а не правило.
- Х-4, Х-38 (деньги предыдущего клиента): нужно событие передачи денег, оно не извлекается.
- Х-32, Х-33 (дверь не закрыта): классификатор двери обучен, но требует отдельной зоны двери на кадре; в автоматическом режиме не подключён.
- Х-15 (инкассаторская сумка без наличных): правило намеренно не выдаёт вердикт, для нормы нужен внутренний регламент банка.
- Х-24, Х-11, Х-28, Х-22, Х-40, Х-46, Х-1, Х-2, Х-13, Х-34, Х-44: правила для этих типов не реализованы или детектор не даёт нужного сигнала.

Это метрики на тех же роликах, из которых брали кадры для обучения детектора; на новых видео точность не измерена.

## Как устроено

```
жюри / браузер ──HTTPS──► Cloudflare quick tunnel ──► api (FastAPI, uvicorn, без ML)
                                                       │ видео → var/jobs/<id>/, задача → SQLite (WAL)
                                                       ▼
                         worker: PyAV (кадры по PTS, 2 кадра/с)
                         → YOLO26s main (14 классов) + YOLO26s hands, PyTorch на CPU
                         → BoT-SORT без ReID (треки людей)
                         → автозоны: стол, дверь, сейф, место кассира по медианам детекций
                         → история сцены → 3 правила → описание и норма из каталога
                         → кадры-доказательства по PTS
                                                       ▼
                               ответ по схеме ТЗ §10 + результат для интерфейса
```

- Процессы `api` и `worker` запускает супервизор `cashguard up`. Процесс API не импортирует ML (проверяет import-linter).
- Задача сохраняется на диск и в SQLite до ответа 200, поэтому перезапуск процесса её не теряет.
- Ручная калибровка под каждое видео не нужна: зоны строятся по найденным предметам, кассир — трек с наибольшим перекрытием стола. Эти зоны — оценка, человек их не подтверждает.
- Лица не распознаются (FAQ 29): роли «кассир», «клиент», «посторонний» определяются по зонам и поведению.
- Детектор сам по себе нарушение не выдаёт: тип и таймкод выдают правила, описание и норма берутся из каталога `configs/catalog/<CODE>.yaml`.

Код: сцена — [src/cashguard/pipeline/scene/](src/cashguard/pipeline/scene/) (`temporal.py`, `auto_zones.py`), правила — [src/cashguard/pipeline/rules/](src/cashguard/pipeline/rules/), сборка результата — [windows_analysis.py](src/cashguard/pipeline/windows_analysis.py). Подробно о режиме: [docs/temporal_workflow.md](docs/temporal_workflow.md).

## Модели

| Роль | Модель | Где работает | Качество на val (PyTorch, 640) | Лицензия |
|---|---|---|---|---|
| Люди и предметы, 14 классов | YOLO26s, обучена на кадрах датасета (эпоха 22) | CPU | mAP50 0,661, mAP50–95 0,533; person AP50 0,93, cash 0,63, safe_open 0,08, cup 0,17 | AGPL-3.0 |
| Руки | YOLO26s, обучена (эпоха 27) | CPU | mAP50 0,925 | AGPL-3.0 |
| Дверь: открыта / закрыта | YOLO26s-cls, обучена (эпоха 6) | в сервисе не используется (нужна зона двери) | F1 closed 0,99, open 0,93 | AGPL-3.0 |
| Треки людей | BoT-SORT без ReID ([configs/trackers/botsort_static.yaml](configs/trackers/botsort_static.yaml)) | CPU | — | AGPL-3.0 |

Веса задаются локальным JSON с путём и sha256 (пример — [configs/local_analysis.temporal.example.json](configs/local_analysis.temporal.example.json)); при несовпадении хеша модель не загружается. Веса и данные в git не хранятся.

Core ML-версии всех трёх моделей экспортированы и проверены на Mac (детектор: 10,6 мс на кадр против 211 мс в PyTorch), но в сервис не подключены: строгое совпадение ответов с PyTorch для детекторов не прошло. Скорости на CPU при 2 кадрах/с хватает для лимита 300 с.

### Эксперимент: дообучение Qwen3.5-4B (в сервисе не используется)

Проверяли, может ли VLM подтверждать кандидатов по кадрам. QLoRA (NF4, r=8) на NVIDIA T4, 202 примера для обучения и 50 для проверки; метки предварительные, сделаны AI, человеком не проверены.

| Модель | С кадрами | Без кадров |
|---|---|---|
| базовая | 12/30, валидный JSON 43% | 16/30 |
| дообученная | 27/30, валидный JSON 100% | 18/30 |

После дообучения ответ зависит от кадров, а не только от текста вопроса. Это совпадение с AI-метками, а не измеренная точность, поэтому адаптер в сервис не подключён; перенос в MLX на Mac не проверялся. В ответе жюри VLM не участвует.

## Как запустить

**Хост:** MacBook Pro M2 Pro, 16 ГБ, macOS. Python 3.12, [uv](https://docs.astral.sh/uv/), pnpm.

1. Окружения:
   ```bash
   uv sync --locked
   ```
   ```bash
   uv run just build-web
   ```
   Для модельного процесса нужно отдельное окружение с `ultralytics`, `torch`, `torchvision`, `lap`, `opencv-python` (extra `ml` в `pyproject.toml`). На нашем Mac использовалась пара torch 2.7.0 / torchvision 0.22.0.
2. Ключи (пишутся в `~/.config/cashguard/.env` с правами 600, на экран не выводятся):
   ```bash
   uv run just gen-key
   ```
3. Конфигурация анализа: скопируйте [configs/local_analysis.temporal.example.json](configs/local_analysis.temporal.example.json), впишите абсолютные пути к весам и включите боевой набор правил:
   ```json
   "temporal_rules": {
     "enabled": true,
     "auto_zones": true,
     "codes": ["VALUABLES_LEFT", "SAFE_OPEN", "THIRD_PERSON_DURING_SERVICE"],
     "min_duration_sec": 2
   }
   ```
4. Запуск (переменные — как в нашем боевом запуске):
   ```bash
   CG_PIPELINE_MODE=full CG_VISION_BACKEND=torch CG_VLM_ENABLED=false \
   CG_LOCAL_MODEL_PYTHON=<путь к python модельного окружения> \
   CG_LOCAL_ANALYSIS_CONFIG=<путь к JSON из шага 3> \
   CG_WEB_DIST=$PWD/web/dist CG_DATA_DIR=$PWD/var CG_UI_RATE_PROFILE=jury \
   HF_HUB_OFFLINE=1 YOLO_OFFLINE=1 PYTHONPATH=src \
   uv run python -m cashguard.cli up --profile prod --port 8137
   ```
5. Публичный адрес:
   ```bash
   cloudflared tunnel --url http://127.0.0.1:8137 --no-autoupdate
   ```
6. Проверка: `/ready` возвращает 200, затем curl из раздела «Проверка через API».

После загрузки весов интернет для обработки видео не нужен (ТЗ, раздел 7): модельный процесс работает с `HF_HUB_OFFLINE=1` и `YOLO_OFFLINE=1`, автоустановка пакетов и сетевые вызовы отключены.

**Разработка (Windows, Linux):** `uv run just setup`, затем `uv run just dev`. Модели не нужны: пайплайн работает в режиме `stub`. Шлюз качества — `uv run just check`.

## Ограничения

- Оценивается 3 типа из 26. `no_violation` означает «по этим трём правилам ничего не найдено», а не «нарушений нет».
- Полнота на открытых роликах низкая: 3 из 20 нарушений. Точность на новых видео и под другим углом камеры не измерена.
- Зоны строятся автоматически по найденным предметам. На новой планировке они могут определиться неверно; если стол не найден, правила не применяются.
- Выход кассира засчитывается по ослабленному критерию: трек заканчивается у двери или края кадра, и до конца ролика в комнате никого нет. Уверенность такого события 0,55.
- Кадры берутся 2 раза в секунду: короткое событие между кадрами можно пропустить.
- Нормы для `THIRD_PERSON_DURING_SERVICE` и `SAFE_OPEN` косвенные.
- Сервис работает на одном Mac через quick tunnel: при перезапуске туннеля меняется адрес, резервного адреса нет.

Полный перечень: [docs/limitations.md](docs/limitations.md).

## Данные и локальность

- Видео жюри не используются для обучения. Папки задач удаляются через 24 часа (`CG_RETENTION_HOURS`).
- Данные хакатона (видео, кадры, разметка) не хранятся в git и не передаются внешним сервисам (FAQ 6).
- Модели загружаются из локальных файлов с проверкой sha256. Туннель только передаёт трафик, обработка идёт на нашем Mac.
- FAQ 35: облачных API и готовых решений нет; только open-source модели и библиотеки (оговорка про AGPL — раздел «Лицензия»). Дообучение Qwen шло на арендованной GPU, но этот адаптер в сервисе не используется.

## Лицензия

- Сервис использует Ultralytics YOLO26 под AGPL-3.0; организаторы подтвердили, что YOLO использовать можно (17.10.2026).
- Сервис доступен по сети, поэтому его код распространяется под AGPL-3.0 ([LICENSE](LICENSE)).
- Для коммерческого использования в банке нужно либо открыть код, либо купить Enterprise-лицензию Ultralytics. Альтернатива — детектор RF-DETR (Apache-2.0).
