## 1. Главное

- Только акты Республики Казахстан: НБРК, АРРФР, тексты с adilet.zan.kz (ТЗ §6, FAQ 30).
- Ссылки без точного пункта допускаются (FAQ 31), но мы всегда даём пункт.
- В датасете нет нарушений, основанных только на внутренних правилах ForteBank (FAQ 32).
- За выдуманные ссылки и неподтверждённые юридические утверждения снимают баллы (критерий 4, 15 баллов).
- Сервис не делает юридических выводов. Результат — подсказка для проверки человеком (ТЗ §7).
- Сила связи:
  - **прямая** — норма описывает именно это действие;
  - **косвенная** — норма задаёт требование, из которого нарушение следует по трактовке;
  - **нет** — прямой нормы в проверенных актах нет, указывается ближайшая и это честно помечено.

## 4. Принцип сопоставления правил с видео

Цепочка от кадра до нормы:

```
кадры (PTS-таймкоды)
  → что видно: люди и предметы (детектор), треки (без лиц), состояния (экран, ключ, дверь, сейф)
  → сцена: зоны по найденным предметам, роли по зонам и поведению, сеансы обслуживания
  → правило типа: обязательный шаг процедуры не наблюдается ИЛИ объект в неверном состоянии
  → кандидат: тип, таймкод, факты для описания, кадры
  → проверка Qwen (только понижает уверенность, нового нарушения не добавляет)
  → тип для жюри (title_ru из каталога)
  → норма из каталога: акт, пункт, дословная цитата, сила связи
  → описание = наблюдаемые факты + почему это может быть нарушением + правовая фраза
  → 1–3 кадра-доказательства
```

Правила отбора:
1. Нарушение выводится только из того, что видно в кадре. Если для вывода нужны данные вне видео, тип не утверждается (ТЗ §7; [limitations.md](limitations.md), разделы 3–6).
2. Почти все нарушения — пропущенный обязательный шаг или неверное состояние объекта. Норма связывается с шагом процедуры, а не с человеком.
3. Норма привязывается к типу, только если она есть в разделе 7 [../analysis/case_analysis.md](../analysis/case_analysis.md). Иначе — сила «нет» или пробел (раздел 9).
4. Найденная норма не означает, что все обстоятельства сцены доказаны. Поэтому для косвенных связей — «Может свидетельствовать о несоблюдении …», а не «нарушен пункт».
5. Сигналы (`SIG_*`) в ответ жюри не попадают и норм в v1 не содержат (контракт `UiSignal` без поля `legal`).

## 5. Карта норм по типам нарушений

Как читать таблицы:
- Первая строка типа — **основная**. Её пункт идёт в правовую фразу описания для жюри. Остальные строки — дополнительные, показываются в интерфейсе.
- «Цитата» — дословная непрерывная подстрока текста акта. Её же кладём в `quote_ru`.
- «Сила» с пометкой «§7» взята из раздела 7. С пометкой «предложение» — наша оценка для отдельной ссылки; её подтверждает S5.
- Названия типов в заголовках скопированы дословно из [violation_catalog.md](violation_catalog.md), раздел 1.1. Источник строки `type` до P0 — violation_catalog.md, раздел 1.1, после — `title_ru` в `configs/catalog/<CODE>.yaml` (владелец S0).
- Сила в этой таблице — источник для `strength` в `configs/catalog/<CODE>.yaml`; контрактный тест P0-S0-05 сверяет их ([roadmap.md](roadmap.md)).

## 6. Как писать правовую фразу в описании

Описание для жюри (`description`) — «что видно на видео и почему это может быть нарушением» (ТЗ §10). Оно собирается по шаблону `template_ru` из фактов правила (`str.format_map`) и заканчивается правовой фразой (`pipeline/legal/describe.py`, владелец S5).

### 6.1. Структура

1. **Наблюдение.** Таймкод и факты: кто (по роли), что сделал, какой предмет, в каком состоянии.
2. **Почему это может быть нарушением.** Связь с шагом процедуры, со словами «может», «не наблюдается».
3. **Правовая фраза.** По силе основной ссылки (первая строка типа в разделе 5).

### 6.2. Правовая фраза по силе связи

| Сила | Шаблон |
|---|---|
| прямая | `Основание: {clause} {act_cite}.` |
| косвенная | `Может свидетельствовать о несоблюдении {clause} {act_cite}.` |
| нет, ближайший пункт есть | `Прямой нормы нет; ближайшая — {clause} {act_cite}.` |
| нет, пункт не определён (FAQ 31) | `Прямой нормы нет; пункт {act_cite} не определён (FAQ 31); требуется проверка человеком.` |

Последняя строка — единственный текст для `none` без пункта. Её используют коды раздела 9 до решения S5 и `OTHER_VISIBLE_IRREGULARITY`. В `LegalRef` у такой записи `clause` пустой, а `act_code` обязателен.

`{act_cite}` — короткая ссылка на акт; хранится в поле `cite_ru` записи акта в `configs/legal/acts.yaml` (раздел 2):

| Код | `act_cite` (`cite_ru`) |
|---|---|
| ПКО | `Правил осуществления кассовых операций…, утв. постановлением Правления НБРК от 29.11.2019 № 231` |
| ПОП | `Правил организации охраны и устройства помещений…, утв. постановлением Правления НБРК от 24.02.2020 № 14` |
| ПОО | `Правил осуществления обменных операций с наличной иностранной валютой…, утв. постановлением Правления НБРК от 04.04.2019 № 49` |
| ТИБ | `Требований к обеспечению информационной безопасности банков…, утв. постановлением Правления АРРФР от 03.04.2026 № 53` |

`{clause}` хранится в каталоге уже с префиксом «п.», как в разделе 5: `п. 20 ч. 1`, `п. 19 пп. 1)`, `п. 73 пп. 6)`. Шаблон префикс не добавляет.

Формы совпадают с [ADR-0006](adr/0006-frozen-jury-contract.md), п. 5. Раздел 7 [../analysis/case_analysis.md](../analysis/case_analysis.md) пишет «о несоблюдении требования…»; в описании жюри слово «требования» не используется, чтобы все документы и снимки тестов совпадали дословно.

### 6.3. Примеры

Хорошо:
- прямая (`RECOUNT_WITHOUT_CLIENT`): «В 13,0 с клиент покидает кассу; принятые наличные кладутся в счётную машинку после его ухода. Пересчёт может проходить не в присутствии клиента. Основание: п. 20 ч. 1 Правил осуществления кассовых операций…, утв. постановлением Правления НБРК от 29.11.2019 № 231.»
- косвенная (`SAFE_KEY_LEFT`): «В 14,0 с кассир покидает кассу; в замке сейфа остаётся ключ. Может свидетельствовать о несоблюдении п. 80 Правил осуществления кассовых операций…, утв. постановлением Правления НБРК от 29.11.2019 № 231.»
- нормы нет (`FOOD_DRINK`): «В 11,0 с кассир подносит стакан ко рту; на столе рядом лежат наличные. Прямой нормы нет; ближайшая — п. 12 ч. 1 Правил осуществления кассовых операций…, утв. постановлением Правления НБРК от 29.11.2019 № 231.»
- бездействие (`NO_CLIENT_ID`): «С 4,0 по 10,0 с клиент передаёт наличные кассиру; предъявление документа клиента в кадре не наблюдается. Основание: п. 19 пп. 1) Правил осуществления кассовых операций…, утв. постановлением Правления НБРК от 29.11.2019 № 231.»

Плохо и почему:

| Плохо | Почему |
|---|---|
| «Кассир нарушил п. 80 ПКО» | юридический вывод о человеке |
| «Кассир похитил часть денег» | квалификация хищения; сервис не вправе (ТЗ §7) |
| «Клиент не был идентифицирован» | утверждение о невидимом: возможна идентификация через сервис цифровых документов или вне кадра |
| «Сумма не совпадает с документом» | сумму и документ по видео не установить |
| «Нарушен п. 16 ПОП» для двери | норма косвенная, к устройству помещения |
| «Вероятно, кассир отвлеклась на телефон и забыла…» | домысел о намерениях; свободный текст |
| «Кассир в розовой кофте…» | описание внешности; роли называются по функции |

### 6.4. Правила

- Нельзя: «нарушил», «нарушен пункт», «является нарушением», «виновен», «умышленно», «незаконно», «хищение», «кража», «украл», «присвоил», «утаил».
- Нельзя утверждать то, чего нет в кадре: суммы, проводки, документы, электронные чеки, полномочия, функции оборудования.
- Можно: «наблюдается», «не наблюдается», «в кадре не видно», «может», «может свидетельствовать».
- Роли — по функции: «кассир», «клиент», «инкассатор», «второй человек», «человек у двери». Без имён и описания внешности.
- Таймкоды в тексте — секунды с одним знаком после запятой: «14,0 с». В поле `timecode_sec` — число.
- Коротко: 2–3 предложения.
- В описание идёт только основная ссылка. Остальные ссылки, цитаты и URL — в интерфейсе (`UiLegalRef`).
- Цитату в описание жюри не вставлять: она есть в интерфейсе. Если всё же нужна — только дословная из раздела 5.
- Свободный текст VLM (`VlmAnswer.note`) в описание не попадает никогда.
- Пункты из раздела 9 (пробелы) в описание не попадают до их сверки.
- Шаблон каждого типа фиксируется снимком syrupy (`tests/unit/legal/`). Отдельный тест на запрещённые слова — предложение S5.

## 10. Как добавить или изменить норму

1. Найти акт на adilet. Только акты РК.
2. Скачать текст через JSON-эндпоинт (раздел 3) и сохранить в `analysis/normative/<КОД>_<орган>_<номер>_<год>_<adilet id>.txt`.
3. Человек сверяет пункт и формулировку и дописывает строку в раздел 7 [../analysis/case_analysis.md](../analysis/case_analysis.md). `analysis/` агенты не правят.
4. Новый акт — в `configs/legal/acts.yaml` (S0). Ссылка — в `configs/catalog/<CODE>.yaml`, поле `legal` (S5).
5. Обновить этот документ (раздел 5 или 9) в том же PR.
6. Прогнать `uv run just check`. Контрактный тест проверяет:
   - каждая `quote_ru` дословно найдена в файле своего акта после схлопывания пробелов (включая неразрывные);
   - цитата непрерывная: без «…» внутри; если нужны два куска — две записи `LegalRef`;
   - `act_code` есть в `acts.yaml`, `url` совпадает с адресом акта;
   - `strength` — одно из `direct`, `indirect`, `none`;
   - у каждого кода с `verdict_impact=true` есть хотя бы одна запись `legal` с `act_code` из `acts.yaml`; `clause` можно опустить только со ссылкой на FAQ 31 (шаблон «нет, пункт не определён»);
   - `strength` в `configs/catalog/<CODE>.yaml` совпадает с разделами 5 и 9 этого документа (источник — этот документ).
7. Перегенерировать `docs/violation_types.md` (`scripts/render_docs.py`) и обновить снимки описаний.
