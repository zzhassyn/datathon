## Статус реализации первой backend-итерации

Реализованы `eval/{labels,metrics,run_eval,report}.py` и `tests/unit/eval/`. Это независимый числовой harness: allowlist разметки, объединение дублей, метрики, отчёт и injected runner seam. Проверка доступной разметки через allowlist подтвердила 40 уникальных видео, 21 положительное, 22 события и 19 чистых; видео и описания кадров не использовались.

До появления S0 Python-контрактов/runner и owner fixtures не заявляются полноценный `eval-replay` по 40 трассам, качество моделей, LOSO, готовая `eval/baselines/main.json` или прохождение G1. Baseline не создаётся из эталонных меток и не перезаписывается при обычном прогоне.

Временная команда при отсутствующих `pyproject.toml`/`uv.lock`/`justfile`:

```sh
PYTHONPATH=src .venv/bin/python -m pytest tests/unit/render tests/unit/eval -q
PYTHONPATH=src .venv/bin/python -m cashguard.eval.run_eval \
  --labels analysis/labels_typed.csv \
  --predictions /path/to/numeric_predictions.json \
  --output /path/to/numeric_report
```

`numeric_predictions.json` содержит только id видео, `verdict`, `events[{code,timecode_sec}]`, при наличии — измеренный `jury_valid`. Утверждённый формат `AnalysisResult` подключается адаптером после мержа S0. По неоценённой схеме `jury_valid_rate=null`, а не 1.0; отчёт отдельно показывает `jury_checked` и `jury_total`. p90 использует линейную интерполяцию type 7. Пропавшие положительные видео считаются FN, пропуски событий — промахами в hit@1s/2s и type accuracy. Сигналы `SIG_*` не входят в вердикт.

Для S0: объявить `jsonschema` как runtime-зависимость renderer, добавить рецепт `eval-replay` после подключения runner и согласовать baseline tolerances. Полный `uv run just check` остаётся зависимым от отсутствующих общих файлов.

## 1. Что и зачем меряем

Жюри оценивает автоматически, по JSON из API (FAQ п. 18). Поэтому каждая метрика ниже привязана к критерию ТЗ (раздел 9).

| Критерий ТЗ | Баллы | Наша метрика | Где считается |
|---|---|---|---|
| 1. Качество обнаружения | 25 | recall, precision, F1 по видео; срабатывания на 19 чистых роликах | `eval-replay`, `loso`, `eval-full` |
| 2. Качество локализации | 15 | \|Δt\|: медиана и p90; hit@1s, hit@2s; валидность кадров-доказательств | `eval-replay`, `eval-full` |
| 3. Качество классификации | 15 | точность типа, матрица ошибок | `eval-replay`, `eval-full` |
| 4. Обоснованность правил | 15 | у каждого нарушения есть правовая ссылка; только действующие акты; цитаты дословно | `eval-*` + `tests/contract` |
| 5. Устойчивость | 10 | LOSO по сценам, искажённые варианты, своя съёмка с других ракурсов | `loso`, `robustness` |
| 6. Готовность продукта | 10 | валидность JSON по замороженной схеме; ответ ≤ 5 мин под нагрузкой | `jury-sim`, `tests/api` |
| 7. Техническое решение | 10 | бюджеты этапов, ≥ 3 ГБ свободной памяти, работа без интернета | `perf` (режим SERVE), холодный старт с выключенной сетью |

Приоритет задаёт FAQ п. 16: пропуск нарушения недопустим, ложных срабатываний — как можно меньше. Отсюда правило всей оценки:
- **recall по видео = 1,0 — жёсткий гейт**;
- precision и всё остальное улучшаем, не трогая recall.

Вердикт оценивается по видео целиком (FAQ п. 15). Допуск по таймкоду не назван: нужен «конкретный кадр и таймкод» (FAQ п. 17). Как жюри сопоставляет строку `type` со своим списком, неизвестно. Поэтому тип меряем против нашего каталога ([violation_catalog.md](violation_catalog.md)).

## 2. Инструменты и где они работают

Рецепты запускаются как `uv run just <рецепт>`. `[macos]` — только на Mac.

|---|---|---|---|

| `just loso` | Windows | подбор порогов `configs/rules/*.yaml` на фолдах L1–L5 и отчёт LOSO | секунды–минуты (оценка) |
| `just eval-full` [macos] | Mac, режим `dev` | реальный пайплайн (Core ML + MLX) на 40 обучающих роликах | порядка 20–40 мин (оценка: ~30 с на типичный ролик) |
| `just perf` [macos] | Mac, только режим `serve` (раздел 8.1) | бюджеты этапов и память на Х-14 и 3 типичных роликах, по одному и внахлёст | проверить замером |
| `just robustness` [macos] | Mac, режим `dev` | искажённые варианты роликов: hflip, поворот ±15°, rot90 (альбомная модель), crop-zoom, перспектива, гамма, 25 fps | проверить замером |
| `just jury-sim URL KEY N` | Windows-ПК через публичный URL, синтетические ролики | N одновременных загрузок по API жюри, опрос раз в 3 с | гейт: N = 5 — каждая задача ≤ 240 с; N = 10 — каждая ≤ 300 с |
| `pytest -m mac` (`tests/mac`) | Mac | паритет Core ML и `.pt`, размещение на ANE, загрузка MLX офлайн, ≥ 3 ГБ свободно на 145-секундном ролике, перекрытие ANE и GPU | минуты (оценка) |

## 3. Эталон: разметка и её нормализация

### 3.1. Источник

Единственный эталон — [analysis/labels_typed.csv](../analysis/labels_typed.csv): колонки `file, label, timecode_sec, type_code, type_ru, what_is_seen, clean_pair, confidence, scene`. `eval/labels.py` читает только `file,label,timecode_sec,type_code,type_ru,clean_pair,confidence,scene`. Столбец `what_is_seen` — свободное описание кадров датасета, то есть тоже данные хакатона ([training.md](training.md), раздел 5.2, правило 5): код оценки его не читает, агенты его не пересказывают. План (S0 с человеком, `analysis/` агенты не правят): перенести `what_is_seen` в файл вне git на Mac (например `data/labels_notes.csv`), а в git оставить только перечисленные столбцы; до этого файл входит в список очистки перед публикацией (P5-S1-01, [roadmap.md](roadmap.md)). Типы в ней — наша разметка по кадрам: организаторы дали только «нарушение / секунда» (FAQ п. 2). `open_labels.xlsx` нужен только для сверки (её делает `training/scripts/01_prepare_raw.py`).

Код сервиса не импортирует `training/` и `kassa_train`. Поэтому `eval/labels.py` повторяет нормализацию из `kassa_train/common.py` сам, а тест сверяет оба варианта на всех 42 именах (предложение).

### 3.2. Нормализация имён X/Х

- `X-1`, `X-2` начинаются с латинской X, остальные — с кириллической Х (U+0425). Без нормализации join с разметкой молча теряет строки.
- Правило: убрать расширение и пробелы, заменить `Х`/`х` на `X`/`x`, перевести в верхний регистр. `'Х-13.mov'` → `'X-13'`.
- Во всех отчётах id — в ASCII (`X-13`).

### 3.3. Дубли: Х-4 = Х-47 — два события, Х-5 = Х-48

- Х-47 побайтно совпадает с Х-4. Это один ролик с двумя нарушениями: формат разметки допускает один таймкод на строку.
  - Х-4: 57 с, `PREV_CASH_ON_DESK`;
  - Х-47 → Х-4: 68 с, `MIXED_CLIENT_CASH`.
- Х-48 побайтно совпадает с Х-5: один чистый ролик.
- При прогоне по файлам (Mac) дубли находятся по sha256, Х-47 и Х-48 отдельно не обрабатываются. В эталоне — по таблице дублей.
- Итого: 42 строки → **40 уникальных роликов: 21 с нарушением (22 события) и 19 чистых**.

### 3.5. Оговорки эталона

- **Разрешение таймкода — 1 с.** Организаторы пишут «22 секунда», «1минута 8 секунда». Как понимать «22 секунда» — t = 22,0 или интервал 21–22 с — проверить. Пока берём значение как есть. |Δt| меньше ~1 с уже на уровне шума разметки.
- **Таймкод означает разное.** Иногда причину (Х-32, Х-33: кассир не закрыла дверь), иногда следствие (Х-30: вошёл посторонний). Поэтому в отчёте есть знаковое Δt по кодам: по нему настраивается `timecode_policy` в каталоге (`event | exit | state_start | omission_due`).
- **Средняя уверенность:** Х-1 (неполная выдача), Х-44 (пропуск проверки подлинности: ПКО п. 41 допускает машинку с проверкой ≥ 2 признаков), Х-47 (смешение денег). Ошибки типа на них разбираем отдельно.
- **Исправления относительно списка команды** ([detection_design.md](../analysis/detection_design.md), раздел «Расхождения PDF с покадровой проверкой»): Х-22 — ключ в замке сейфа, а не незаблокированный компьютер; Х-38 — деньги первого клиента на столе при входе следующего.

## 4. Метрики

Все метрики считаются по `AnalysisResult` (`analysis.json`) каждого видео: вердикт, коды, таймкоды, правовые ссылки, уровень результата. Проверки формы JSON (схема, base64, кадры) считаются по `jury.json`. В режиме replay кадров нет, поэтому полная проверка кадров и схемы — в `eval-full`, `jury-sim` и `tests/contract`.

Сигналы `SIG_*` в метрики вердикта не входят: в ответ жюри они не попадают. Отчёт показывает их числом срабатываний.

### 4.1. Обнаружение (по видео)

| Обозначение | Определение |
|---|---|
| TP | ролик с нарушением, вердикт `violation` |
| FN | ролик с нарушением, вердикт `no_violation` |
| FP | чистый ролик, вердикт `violation` |
| TN | чистый ролик, вердикт `no_violation` |
| recall | TP / (TP + FN), по 21 ролику |
| precision | TP / (TP + FP) |
| F1 | 2 · precision · recall / (precision + recall) |
| доля чистых без срабатываний | TN / 19 |

Вердикт засчитывается по видео целиком, независимо от кода и времени. Совпадение кода и времени меряют следующие метрики.

### 4.2. Сопоставление событий

Для каждого ролика: эталонные события E (0, 1 или 2 — у X-4 два) и предсказанные нарушения P (не больше 5).
1. Пары (e, p) сопоставляются один к одному по возрастанию |t_p − t_e|, без ограничения окна. Код при сопоставлении не учитывается.
2. Эталонное событие без пары — пропуск события.
3. Предсказание без пары в ролике с нарушением — лишнее событие. В чистом ролике — срабатывание на чистом (раздел 6).

Алгоритм — предложение S1. Жюри могло бы сопоставлять иначе, поэтому отчёт хранит и сырые пары.

### 4.3. Локализация

| Метрика | Определение |
|---|---|
| \|Δt\| медиана, p90 | по сопоставленным парам, Δt = t_pred − t_label, в секундах |
| знаковая медиана Δt по коду | систематический сдвиг: «+» — ставим позже разметки, «−» — раньше |
| hit@1s, hit@2s | доля из 22 эталонных событий, у которых есть пара с \|Δt\| ≤ 1 с / ≤ 2 с. Пропуск события считается промахом |
| валидность кадров | доля нарушений, где: 1–3 кадра; `evidence_frames[0].timestamp_sec == timecode_sec`; все `timestamp_sec` в [0, длительность]; `image_base64` начинается с `/9j/`, без префикса `data:`, и декодируется как JPEG. Цель — 1,0 |

Релевантность кадра автоматически не меряется. Её проверяют люди: перед тегом `jury-v1` открывают кадры каждого нарушения `eval-full` на 21 ролике и записывают в отчёт только «да/нет» по каждому нарушению (карточка P4-H-02 в [roadmap.md](roadmap.md), гейт G4: релевантных = 100 %, протокол в PR тега; раздел 12).

### 4.4. Классификация

| Метрика | Определение |
|---|---|
| точность типа | доля эталонных событий, у которых код сопоставленного предсказания совпал с эталоном. Пропуск — ошибка |
| тип найден где-то в ролике | доля эталонных событий, чей код есть среди предсказаний этого ролика |
| матрица ошибок | эталонный код × предсказанный код по парам, плюс столбец «пропуск» |
| неизвестные строки `type` | каждая строка `type` в `jury.json` должна быть `title_ru` из каталога. Цель — 0 неизвестных |

### 4.5. Правовая ссылка

Для каждого нарушения в ответе:
1. В `description` есть правовая фраза одного из четырёх видов (шаблоны дословно — [legal_sources.md](legal_sources.md), раздел 6.2):
   - прямая норма: `Основание: {clause} {act_cite}.`;
   - косвенная: `Может свидетельствовать о несоблюдении {clause} {act_cite}.`;
   - нормы нет, есть ближайший пункт: `Прямой нормы нет; ближайшая — {clause} {act_cite}.`;
   - пункт не определён (FAQ 31): `Прямой нормы нет; пункт {act_cite} не определён (FAQ 31); требуется проверка человеком.`
2. Вид фразы соответствует силе нормы (`strength`: direct / indirect / none) в `configs/catalog/<CODE>.yaml`.
3. Акт и пункт входят в правовые ссылки этого кода в каталоге, а акт — в `configs/legal/acts.yaml` со статусом «действует».
4. Нигде нет утративших силу актов: НБРК № 58 (2001), № 250 (2012), № 48 (27.03.2018), № 254 (24.08.2012).

Метрика — доля нарушений, прошедших все четыре проверки. Цель — 1,0. Дословность цитат (`quote_ru` есть в `analysis/normative/*.txt`) проверяет `tests/contract`, а не прогон оценки. Источник норм — [case_analysis.md](../analysis/case_analysis.md), раздел 7, и [legal_sources.md](legal_sources.md).

### 4.6. Валидность схемы

Каждый ответ `GET /api/v1/jobs/{id}` (и `processing`, и `done`, и `failed`) проверяется по замороженной схеме `src/cashguard/contracts/schemas/jury_job.schema.json` и инвариантам:
- `done` ⇒ `verdict` не `null`; `verdict == "violation"` ⇔ нарушений ≥ 1;
- `processing` и `failed` ⇒ `verdict: null`, `violations: []`;
- не больше 5 нарушений, по возрастанию времени;
- `timecode_sec = round(pts_event, 2)`, в [0, длительность]; все `timestamp_sec = round(pts, 2)` той же функцией, поэтому `evidence_frames[0].timestamp_sec == timecode_sec` точно;
- никаких лишних ключей.

Метрика — доля валидных ответов. Цель — 1,0. Любой невалидный ответ блокирует выпуск.

### 4.7. Уровни результата

Каждая метрика считается дважды:
- по **предварительному результату** (только правила, `result_level=rules`);
- по **финальному** (после VLM, `result_level=full`).

VLM может только понизить балл кандидата. Значит, recall финального результата не выше recall предварительного. Предварительный результат уходит жюри, если VLM пропущен под нагрузкой. Поэтому **recall = 1,0 обязателен для обоих уровней**. Если recall финального ниже предварительного, VLM понизил настоящее нарушение. Это ошибка вопроса VLM (S6) или порога τ_final.

В replay ответы VLM берутся из записанных при `extract-signals` и `eval-full`. Запись идёт по ключу (ролик, окно ±2 с, вопрос) для всех окон выше низкого предпорога, а не только для кандидатов текущих правил. Если правила изменились и дали кандидата, для которого записанного ответа нет, replay считает это «VLM пропущен» (уровень правил), а не «нет». Поэтому replay не годится для подбора τ_final: τ_final подбирается только по `eval-full` (P3-S5-01). В `eval-full` VLM работает по-настоящему. Ролики идут по одному, поэтому деградаций быть не должно. Если в `eval-full` у ролика `result_level` не `full`, отчёт помечает это отдельно.

## 5. LOSO по сценам L1–L5

### 5.1. Зачем

Финальное видео снимут под другим углом (FAQ п. 4). LOSO (leave-one-scene-out) имитирует это на наших данных: пороги подбираются на четырёх сценах и проверяются на пятой, которой при подборе не было.

### 5.2. Фолды

| Фолд (отложена) | Роликов | С нарушением | Чистых | Событий |
|---|---|---|---|---|
| L1 | 9 | 5 | 4 | 6 |
| L2 | 17 | 8 | 9 | 8 |
| L3 | 3 | 2 | 1 | 2 |
| L4 | 6 | 4 | 2 | 4 |
| L5 | 5 | 2 | 3 | 2 |
| Всего | 40 | 21 | 19 | 22 |

Почти каждый код встречается только в одной сцене. В двух сценах есть только `DOOR_NOT_CLOSED` (L3, L4) и `PREV_CASH_ON_DESK` (L1, L5). `PC_UNLOCKED` и `VALUABLES_LEFT` — только в L2. Значит, когда отложена сцена кода, в обучающих фолдах у него нет ни одного положительного примера. LOSO для такого кода проверяет логику правила и его порог по умолчанию, а не подобранный порог. Так и задумано: тест на новом ракурсе устроен так же.

### 5.3. Процедура `just loso` (предложение S1; S4/S5 могут уточнить)

Для каждого кода c и фолда k:
1. Обучающая часть — четыре сцены, кроме L_k.
2. Если в обучающей части есть положительные примеры c: τ_c,k — наибольший порог, при котором все они остаются выше порога (запас — параметр в `configs/rules/<CODE>.yaml`, проверить).
3. Если примеров нет: τ_c,k = порог по умолчанию из `configs/rules/<CODE>.yaml`.
4. Предсказания для роликов L_k считаются с порогами τ_·,k.

Итог:
- **LOSO recall по видео** — по 21 ролику, каждый предсказан в своём отложенном фолде. Гейт — 1,0.
- Порог в `configs/rules/<CODE>.yaml` для работы: не выше min_k τ_c,k и не выше наименьшего балла настоящих нарушений c на всех 40 роликах. При выборе между recall и ложными срабатываниями побеждает recall (FAQ п. 16).
- τ_final (после VLM) подбирается на `eval-full` с тем же условием: LOSO recall = 1,0.

### 5.4. Оговорка про perception

Детектор обучен со сценой L4 в валидации ([training.md](training.md), раздел 9). Трассы роликов L1, L2, L3, L5 сняты детектором, который видел эти сцены при обучении. Поэтому LOSO порогов на этих сценах оптимистичен по perception. Честный от начала до конца только фолд L4. Ещё один честный тест — своя съёмка с других ракурсов (раздел 7).

### 5.5. Что в отчёте LOSO

- По каждому фолду: recall, precision, срабатывания на чистых, медиана |Δt|, точность типа.
- По каждому коду: τ_c,k по фолдам, баллы положительных примеров, ближайший к порогу балл на чистых роликах (запас с обеих сторон).
- Ролики, пойманные с запасом меньше заданного, — список «на грани».

## 6. Защита чистых роликов

19 чистых роликов — это определение нормы от организаторов. Правило: **ни один код, влияющий на вердикт, не должен срабатывать на чистых роликах**. Сигналы срабатывать могут: в ответ жюри они не попадают.

- Проверка идёт в каждом `eval-replay`. Отчёт `clean_firings` — для каждого чистого ролика список кодов, которые сработали, с баллом и τ.
- Гейт для PR с правилом: **ни одного нового срабатывания** относительно базовой линии.
- Новое правило из группы B1 ([detection_design.md](../analysis/detection_design.md), раздел «Покрытие списка команды») включается только после прогона на 19 чистых роликах без срабатываний. Если оно срабатывает на чистых, оно становится сигналом (группа B2).
- Трудные чистые ролики: Х-8, Х-10, Х-43, Х-45 (кассир пересчитывает одна, без второго сотрудника), Х-5 (два клиента подряд, телефон в руках у клиента), Х-14 (кассир вскрывает сумку без инкассатора, самый длинный ролик). Их срабатывания разбираем первыми.
- Если recall 1,0 на LOSO и ноль срабатываний на чистых несовместимы, побеждает recall. Тогда в гейте G4 precision показывается честно, а случай записывается в [limitations.md](limitations.md).

## 7. Устойчивость

### 7.1. Искажённые варианты (`just robustness`, Mac)

Каждый из 40 роликов прогоняется через реальный пайплайн в нескольких вариантах:

| Вариант | Что проверяет |
|---|---|
| hflip | зеркальная раскладка: зоны строятся по предметам, а не по пикселям |
| поворот ±15° | наклон камеры |

Отчёт по каждому варианту: recall и precision по видео, срабатывания на чистых, медиана |Δt| и её сдвиг относительно оригинала, точность типа. На `rot90` в логе видно, что использован `det_480x864`, а `/ready` не падает при ленивой загрузке. Прогон — карточка P4-S3-01 в [roadmap.md](roadmap.md).

Искажённые ролики — производные от данных хакатона. Они создаются временно в `var/eval/` (вне git) и удаляются после прогона (предложение).


### 7.2. Своя съёмка с других ракурсов (FAQ п. 7)

Самый сильный тест на новый ракурс. По README обучения хватит даже 10–15 коротких роликов с 2–3 других ракурсов.

- Разметка — в том же формате, что `labels_typed.csv`, со своими кодами сцен (предложение: `O1`, `O2`…). Путь — `data/raw/own/` (предложение, [training.md](training.md), раздел 5).
- Ракурсы делим: часть идёт в обучение, хотя бы один ракурс — только в оценку. Иначе тест перестаёт быть честным.
- Своя съёмка — единственный способ измерить recall типов группы B1, которых нет в датасете: телефон у кассира, уход во время обслуживания и другие. И способ проверить их на ложные срабатывания в чистых сценах.
- Отчёт по своей съёмке — отдельный блок, он не смешивается с метриками 40 роликов.

## 9. Симуляция жюри

### 9.1. Правило 5 минут

Ролик без ответа за 5 минут считается необработанным (ТЗ раздел 10, FAQ п. 14). Жюри считает время от своего POST, и загрузка по их каналу тоже входит в эти 5 минут. Наши сроки отсчитываются от t0 — начала приёма запроса — с запасом: цель — всё готово ≤ 240 с.

### 9.2. `just jury-sim URL KEY N`

- Запуск с Windows-ПК, подключённого к раздаче с телефона (мобильная сеть), через публичный URL — так, как будет у жюри. Переключение ПК на точку доступа делает человек.
- N загрузок одновременно по `POST /api/v1/analyze`, опрос `GET /api/v1/jobs/{id}` раз в 3 с.
- `KEY` — командный ключ: для `/api/v1` ключи `jury` и `team` равноправны.
- Время каждой задачи — от начала её POST до первого ответа со `status: done`.
- Каждый ответ (и `processing`, и `done`) проверяется по замороженной схеме (раздел 4.6).

| Прогон | Гейт |
|---|---|
| N = 5 | все `done` ≤ 240 с от своего POST; 0 ответов 5xx; все ответы валидны по схеме |
| N = 10 (из них ≥ 3 ролика по 145 с) | жёсткий гейт: каждая задача `done` ≤ 300 с от своего POST (цель ≤ 270 с); лишние — `result_level=rules` или `perception_min`; 0 ответов 5xx и 0 `failed`. Если гейт не пройден — настраиваем уровень `min` и рубеж `perception_hard_stop` в `configs/deadlines.yaml` (S1), а не записываем провал в ограничения |
| N ≥ 15 (по желанию) | измеренный предел пропускной способности; итог — в [limitations.md](limitations.md) |
| тот же файл дважды | второй ответ — сразу (кэш результатов по sha256) |
| запрос без ключа | 401 |
| `.txt` вместо видео | 415 |

Ролики для `jury-sim`. Видео и кадры датасета живут только на Mac ([training.md](training.md), раздел 5.2, правило 1); на Windows-ПК работают агентские сессии (Claude Code, Codex), поэтому ролики датасета туда не копируются. Решение:
- гейты N = 5 и N = 10, проверки с мобильной сети и проверка Funnel — на синтетических клипах `scripts/make_synthetic_mov.py` (свой sha256 у каждого, среди них ролики по 145 с) или на своей съёмке команды. Синтетика проверяет только время и форму ответа;
- реалистичная пачка на роликах датасета — только с ноутбука человека, на котором нет агентских сессий; ролики копируются по LAN, без облачных хранилищ, и удаляются после прогона.

Качество ответов (не только время) меряют `eval-full` на Mac и своя съёмка. Видео через туннель проходят через Cloudflare так же, как пойдут видео жюри; кэширование `/api` выключено.

### 9.3. Связанные проверки

- `scripts/smoke_jury.sh` — точный curl из ТЗ + опрос до `done`.
- Проверка холодного старта без сети (человек): сеть выключена → `just services-restart` → `/ready` 200 (прогрев всех моделей) → curl из ТЗ на 3 роликах на `127.0.0.1` → `done`. Так видны и сетевые вызовы при импорте и старте процессов (HF hub, настройки и ассеты Ultralytics). Это доказательство, что для обработки не нужен интернет (ТЗ раздел 7).
- Проверки с отказами (дважды, по [jury_mode.md](jury_mode.md)): kill -9 perception посреди задачи, затем VLM; SIGSTOP perception; сеть пропадает на 30 с; 10 параллельных загрузок; `.txt`; повёрнутый HEVC-ролик с телефона; 145-секундный ролик в пачке; перезагрузка и вход. После каждой — все задачи `done` с валидным JSON.

## 10. Базовая линия и регрессионные гейты

### 10.1. `eval/baselines/main.json`

Коммитится в git. Владелец — S1. PR правил и PR выпуска моделей прикладывают только дифф `eval-replay`; саму базовую линию после каждого мержа перегенерирует S1 одним последовательным PR, чтобы параллельные PR не правили один файл ([roadmap.md](roadmap.md), раздел 4.5). Только числа, коды и id роликов; никаких кадров и описаний. Форма — предложение S1, фиксируется первым PR оценки:

```json
{
  "schema_version": 1,
  "created_at": "<ISO 8601>",
  "source": "replay",
  "git_sha": "<sha>",
  "models_hash": "<hash>",
  "config_hash": "<hash>",
  "metrics": {
    "rules":  {"video_recall": "<>", "video_precision": "<>", "f1": "<>", "loso_video_recall": "<>",
               "dt_median": "<>", "dt_p90": "<>", "hit_1s": "<>", "hit_2s": "<>",
               "type_accuracy": "<>", "legal_ok_rate": "<>", "clean_firings": "<>"},
    "final":  {"...": "те же поля"}
  },
  "per_video": {"X-1": {"verdict": "violation", "codes": [["CASH_WITHHELD", "<t>"]]}, "X-3": {"verdict": "no_violation", "codes": []}},
  "clean_firings": {"X-8": [], "X-10": []},
  "tolerance": {"video_precision": "<>", "type_accuracy": "<>", "dt_median": "<>"}
}
```

Допуски (`tolerance`) задаются при первой базовой линии (проверить значения с S0). До этого любое ухудшение precision, точности типа или медианы |Δt| разбирает человек.

Обновление базовой линии — отдельный явный шаг, не побочный эффект прогона. Имя флага или рецепта — на усмотрение S1 (предложение: `cashguard eval --update-baseline`). Если базовая линия построена на трассах старой модели (`models_hash` не совпадает с текущими трассами), `eval-replay` предупреждает об этом.

### 10.2. Гейт PR (каждый PR, протокол слияния)

1. Ребейз на `main`, затем `uv run just check`: ruff, basedpyright, lint-imports, `pytest -m 'not mac and not slow'`, `biome ci`, `tsc -b`, проверка дрейфа схем и OpenAPI.

   - LOSO recall по видео = 1,0;

   - нет новых срабатываний кодов вердикта на чистых роликах.
3. Каждое правило приходит с позитивными и негативными фикстурами таймлайнов (`tests/fixtures/timelines/<CODE>_{pos,neg}_*.json`), записью каталога с правовой ссылкой, чья цитата дословно есть в `analysis/normative` (контрактный тест), и snapshot-тестом шаблона описания.
4. PR выпуска модели — по [training.md](training.md), раздел 16: паритет, новые трассы, тот же diff `eval-replay`, `just perf`.

## 11. Отчёты: где лежат и как читать

### 11.1. Где

Предложение S1 по раскладке:

```
var/eval/<UTC-время>__<вид>/        # вид: replay | loso | full | perf | robustness | jury_sim
├─ report.md          # сводка: гейты, diff с базовой линией, таблицы
├─ metrics.json       # все числа раздела 4, для обоих уровней результата
├─ per_video.csv      # строка на ролик
├─ per_event.csv      # строка на эталонное событие и сопоставленное предсказание
├─ clean_firings.csv
├─ confusion.csv
└─ loso.json | perf.json | robustness.json | jury_sim.json
```

`var/` закрыт для чтения агентами (`.claude/settings.json`). Поэтому каждый рецепт печатает сводку и diff с базовой линией в stdout: агент видит вывод команды, а PR прикладывает этот diff. Числовые отчёты обучения в `runs/` (`results.csv`, `timing.json`, `eval_*.md/json`) агентам читать можно, картинки `runs/**/*.jpg` — нет ([../AGENTS.md](../AGENTS.md), правило 4). Нужна ли отдельная папка для числовых отчётов eval вне `var/` — проверить с S0.

### 11.2. Порядок чтения

1. **Строка гейтов** вверху `report.md`: каждый гейт — «да» или «нет», с числом и порогом. Есть «нет» — дальше читать только его.
2. **Diff с базовой линией**: какие метрики изменились и в какую сторону.
3. **Таблица по роликам** (`per_video.csv`): видео, сцена, эталон (вердикт, события), наш вердикт, уровень результата, коды с таймкодами, Δt пар, совпадение типа, отметка «на грани».
4. **Срабатывания на чистых** (`clean_firings.csv`): код, балл, τ, запас.
5. **Локализация**: медиана и p90 |Δt|, hit@1s/2s, знаковая медиана Δt по коду.
6. **Матрица ошибок типа.**
7. **Правовые ссылки и схема**: список нарушений, не прошедших проверку.
8. **Сигналы**: число срабатываний по кодам `SIG_*`, только для информации.

### 11.3. Типичные диагнозы

| Симптом | Вероятная причина | К кому |
|---|---|---|
| Ролик с нарушением пропущен, кандидат есть, но ниже τ | τ слишком высокий | владелец правила (S4/S5), `configs/rules/<CODE>.yaml` |
| Ролик с нарушением пропущен, кандидата нет | perception не видит предмет (смотреть AP50 класса в `eval_val.md`) или неверные зоны и роли | S3 (детектор) или S4 (сцена) |
| Recall финального ниже предварительного | VLM понизил настоящее нарушение | S6 (вопрос, кадры) или τ_final |
| Вердикт верный, тип неверный | два правила конкурируют за один эпизод; слияние кандидатов | владельцы обоих правил, S5 (verdict) |
| Δt систематически «+» или «−» по коду | `timecode_policy` не совпадает со смыслом разметки (причина или следствие) | владелец кода, каталог |
| Новое срабатывание на чистом ролике | правило ловит обычную работу | владелец правила: уточнить логику или перевести в сигнал; recall не снижать |
| Невалидный `jury.json` | рендер или безопасный запасной рендер | S1, блокирует выпуск |
| Нет правовой фразы или неверная сила нормы | запись каталога | S5, S0 |
| Провал только на одном искажённом варианте | зоны в пикселях, порог размера, ориентация | S4 (зоны) или S3 |
| `perf`: этап вышел за бюджет | гейтинг позы, частота кадров, квантизация | S3 (perception), S6 (VLM) |
| `jury-sim`: задачи позже 240 с (N = 5) или 300 с (N = 10) | очередь, сроки, лестница деградации, уровень `min`, `perception_hard_stop` | S1 |

## 12. Данные и агенты в оценке

- `eval-replay` и `loso` работают только с числовыми трассами `var/signals/*.json.gz` и столбцами `labels_typed.csv` без `what_is_seen` (раздел 3.1). Это безопасно для агентов на Windows.
- `eval-full`, `perf`, `robustness` читают ролики датасета на Mac. Их запускает человек или сессия S3/S6 на Mac. Агент не открывает кадры и не пересказывает их.
- Ручная проверка кадров-доказательств — только люди (P4-H-02). В отчёт попадает только «да/нет» по нарушению.
- Ролики датасета на Windows-ПК не копируются; `jury-sim` и проверки с мобильной сети идут на синтетике (раздел 9.2).
- Видео жюри и UI никогда не попадают в `var/signals`, `data/`, обучение или оценку. Тестовые видео жюри нельзя использовать для обучения (ТЗ раздел 10).
- Отчёты содержат числа, коды, id роликов и пути. Ни base64, ни встроенных кадров.
- Трассы между машинами — только `just sync-signals` (scp по LAN или Tailscale), никогда через облачные хранилища.
- Подробно о правилах данных — [training.md](training.md), раздел 5.
