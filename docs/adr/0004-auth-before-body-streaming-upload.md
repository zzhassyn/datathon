# ADR-0004. Проверка ключа до чтения тела, потоковая загрузка; POST отвечает 200 только после того, как задача стала долговечной

> Назначение: зафиксировать порядок обработки `POST /api/v1/analyze` (и `POST /api/ui/jobs`) от первого байта до ответа.
> Владелец: S0 (документ); реализует S1 (`api/upload.py`, `api/ingest_service.py`, `api/deps.py`, `api/routes/jury.py`). Статус: черновик v1, 17.10.2026.

## Статус

Принято.

## Контекст

- ТЗ §10: ключ передаётся в заголовке `X-API-Key`; запросы без верного ключа сервис отклоняет. Видео .mov в поле `file`; в ответ `job_id`.
- Файл около 29 МБ (FAQ 1, 25). Пример из ТЗ: `curl -X POST … -H "X-API-Key: <ключ>" -F "file=@video_017.mov"`. curl отправляет часть с `Content-Type: application/octet-stream`.
- FastAPI разбирает тело формы **до** разрешения зависимостей. Параметр `UploadFile` заставил бы сервер принять и записать 29 МБ неаутентифицированных данных до проверки ключа.
- Cloudflare: лимит тела 100 МБ на бесплатном плане, таймаут origin 100 с. Keep-alive cloudflared к origin — 90 с; если uvicorn закроет соединение раньше, неповторяемый POST может получить 502.
- Автоматический проверяющий жюри неизвестен. 200 безопаснее, чем 202.
- После ответа с `job_id` задача не должна теряться.

## Решение

1. Обработчик принимает **только** `request: Request`. Никаких `UploadFile`, `Form`, `await request.body()`.
2. Зависимость роутера `require_api_key`:
   - `APIKeyHeader('X-API-Key', auto_error=False)`;
   - sha256 присланного ключа сравнивается через `hmac.compare_digest` с **каждым** ключом из `CG_API_KEYS` (principals `jury` и `team`), без раннего выхода;
   - ошибка → 401 JSON, тело не читается.
3. `t0` фиксируется здесь: после ключа, до первого байта тела ([ADR-0005](0005-deadline-tiers-provisional-degradation.md)).
4. Ранние отказы: `Content-Length` > `CG_MAX_UPLOAD_MB` (100) → 413; свободно на диске < 2 ГБ → 507.
5. Поток: `request.stream()` → `StreamingFormDataParser` (streaming-form-data 2.1.0):
   - поле `file` пишется в `var/jobs/{id}/input.part` с бегущим sha256 и счётчиком байт;
   - превышение лимита → 413, `.part` удаляется;
   - Content-Type части любой, имя файла клиента игнорируется;
   - нет поля `file` → 422.
6. Сигнатура: байты `[4:8]` ∈ {`ftyp`, `moov`, `mdat`, `wide`, `free`, `skip`, `pnot`}, иначе 415. Расширение и Content-Type не проверяются.
7. `fsync` в потоке, затем `os.replace` в `input.mov`.
8. Лёгкий probe PyAV (≤ 50 мс): длительность, размеры, кодек, поворот. Нечитаемый контейнер → 415.
9. Дедупликация по sha256 (`result_cache` или связанная задача в работе), иначе `INSERT jobs` и событие `accepted`.
10. `COMMIT`, затем HTTP **200** `{"job_id": "<32-hex uuid4>"}`.
11. Алиас `POST /api/v1/analyze/` скрыт из OpenAPI: слэш в конце не даёт 307.
12. Тело multipart в OpenAPI описывается через `openapi_extra`, потому что обработчик принимает сырой `Request`.
13. uvicorn: `--timeout-keep-alive 100` (больше 90 с keep-alive cloudflared), `--limit-concurrency 64`.
14. Тот же `ingest_upload` обслуживает `POST /api/ui/jobs` с principal `ui` ([ADR-0008](0008-separate-ui-api.md)).

## Рассмотренные альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Параметр `UploadFile` / `Form` | FastAPI разбирает и спулит форму до зависимостей: 29 МБ без проверки ключа |
| `await request.body()` | Весь файл в памяти. Нет раннего 413. Двойная запись при сохранении |
| Ответ 202 Accepted | Неизвестный автоматический проверяющий может ждать 200 |
| Проверка по расширению или Content-Type | curl шлёт `application/octet-stream`, имя файла произвольное. Проверка сигнатуры ISO-BMFF надёжнее |

## Последствия

Плюсы:
- 401 до чтения хотя бы одного байта тела.
- Ранний 413. Одна запись на диск. sha256 «бесплатно» для дедупликации и кэша результатов.
- После 200 задача долговечна: файл на диске после fsync, строка зафиксирована.

Минусы и цена:
- Обработчик сложнее идиоматичного FastAPI. Агенты будут склонны «упростить» его до `UploadFile`. Защита — отдельный тест.
- Документацию тела в OpenAPI нужно вести вручную.
- streaming-form-data — дополнительная зависимость.

Что проверяет решение:
- `tests/api/test_auth_before_body.py`: при 401 итератор тела не потребляется.
- `tests/api`: 401, 413, 415, 422, 507, слэш в конце, 5 параллельных загрузок, дедупликация.
- schemathesis: нет 5xx, ключ на каждом маршруте `/api/v1`.
- Репетиция со сбоями: загрузка файла `.txt` → 415.
