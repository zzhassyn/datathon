# ADR-0010. Qwen3.5-4B через mlx-vlm как ограниченный верификатор, который может только понижать баллы

> Назначение: зафиксировать роль VLM в пайплайне, её параметры и границы влияния на вердикт.
> Владелец: S0 (документ); реализуют S6 (`pipeline/vlm/**`, `workers/vlm_worker.py`, `configs/vlm.yaml`) и S5 (`pipeline/verdict/decide.py`). Статус: черновик v1, 17.10.2026.

## Статус

Принято. Открытый вопрос grill-me: влияют ли находки keyframe pass на вердикт (умолчание — только сигналы; `OTHER_VISIBLE_IRREGULARITY` — только с подтверждением треками и выше высокого τ).

## Контекст

- Правила дают точный тип и таймкод (15 + 15 баллов), но срабатывают на похожих чистых роликах (Х-8, Х-10, Х-43, Х-45, Х-5, Х-14).
- FAQ 16: ложных срабатываний как можно меньше, пропуск недопустим.
- FAQ 9: в тесте могут быть типы, которых нет в обучении.
- ТЗ §7: описание без неподтверждённых предположений; облачные модели запрещены.
- Память: на пике ≥ 3 ГБ свободно. По [detection_design.md](../../analysis/detection_design.md): Qwen3.5-4B (VideoMME 76,9) против Qwen3.5-9B (78,4) — 9B в 4-bit оставляет лишь ≈ 1,5–2,5 ГБ; Qwen3-VL-4B слабее (69,3).
- mlx-vlm держит thread-local stream; модель можно вызывать только из одного потока.
- Только VLM: грубые таймкоды, нестабильные названия типов, пропуск мелочей вроде ключа в замке.

## Решение

1. **Отдельный vlm worker**, модель только из главного потока ([ADR-0002](0002-three-process-runtime-supervisor.md)).
2. **Модель:** Qwen3.5-4B из mlx-community, закреплённые ревизии:

   | Квантизация | Ревизия | Веса |
   |---|---|---|
   | 8-bit (основная) | `1704583a` | 5,16 ГБ |
   | 6-bit | `fbb1092a` | 4,11 ГБ |
   | 4-bit | `0e7ffd5c` | 3,06 ГБ |

   `CG_VLM_QUANT=auto`: после загрузки 8-bit и прогрева максимального размера, если psutil available < 3,0 ГБ — 6-bit, затем 4-bit. Выбор виден в `/ready` и `workers.quant`. Загрузка из `models/hf/<repo>` с `HF_HUB_OFFLINE=1`; отсутствующий файл — громкая ошибка.
3. **Генерация:** mlx-vlm `stream_generate`, `enable_thinking=False`, temperature 0, llguidance JSON-schema processor (собирается один раз при старте), `max_tokens` 96 для проверки и 160 для keyframe pass. Дедлайн `vlm_stop` проверяется на каждом чанке ([ADR-0005](0005-deadline-tiers-provisional-degradation.md)).
4. **Память:** `mx.set_cache_limit(1 ГБ)`, `mx.set_memory_limit(7 ГБ)`, `mx.clear_cache()` после каждой задачи. VLM-этап задачи — только при свободной памяти ≥ 3,0 ГБ (`CG_MIN_FREE_MEM_GB`; формула — [architecture.md](../architecture.md), раздел 8). 8-bit остаётся для окна жюри, только если `just perf` в SERVE показал ≥ 3 ГБ свободно на пике, иначе `CG_VLM_QUANT=6bit`.
5. **Группировка:** кандидаты с якорями в пределах ±2 с — один вызов с несколькими вопросами. Группы упорядочены по `|score − τ|` по возрастанию (сначала то, что может перевернуть вердикт).
6. **Вход на группу:** 4–8 кадров из хранилища кадров в масштабе ≈ 0,75 и одна мозаика увеличенных фрагментов; вопросы `vlm_question_ru` из каталога; метки времени кадров — в тексте промпта.
7. **Ответ:** `VlmAnswer{answers: [{qid, a: yes|no|unclear, c}], note ≤ 200 символов}`. `note` — только для UI и отладки, никогда в описание жюри.
8. **Влияние на вердикт:** ответ «нет» понижает score и **никогда** не повышает. Пониженный кандидат остаётся в UI с пометкой «снижено VLM» (`vlm_status=downweighted`). `τ_final` подбирается на eval-full с сохранением LOSO recall 1.0.
9. **Keyframe pass** (если остался бюджет): 12–16 кадров половинного разрешения на входах, выходах и сменах состояний → `KeyframeFinding`. По умолчанию — только сигналы. `OTHER_VISIBLE_IRREGULARITY` влияет на вердикт, только если подтверждён треками и выше высокого τ.
10. **Бэкенды** за портом `VlmBackend`: `mlx` (Mac), `transformers` (Linux, extra `cuda`), `replay` (записанные ответы для eval на Windows), `null`.

## Рассмотренные альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Пайплайн только на VLM | Грубые таймкоды, нестабильные типы, пропуск мелких состояний; теряются баллы локализации и классификации |
| Qwen3.5-9B в 4-bit | Нарушает правило ≥ 3 ГБ свободной памяти; выигрыш на видео небольшой |
| Режим thinking | Медленно и непредсказуемо по длине |
| Свободный текст с разбором regex | Хрупкий разбор; схема гарантирует форму ответа |
| `mlx_vlm.server` по HTTP | Лишний сервер и протокол; нет контроля дедлайна на чанке |
| 4-bit по умолчанию | Ниже качество; 8-bit помещается, понижение — только по замеру памяти |

## Последствия

Плюсы:
- Точность растёт без потери recall: VLM только понижает.
- Каждый вызов ограничен (≈ 3–5 с на группу, оценка) и прерываем.
- Схема даёт детерминированный разбор ответа.

Минусы и цена:
- По умолчанию VLM не добавляет новых нарушений в вердикт. Новый тип вне правил может быть пропущен (риск, [limitations.md](../limitations.md)).
- Квантизация зависит от свободной памяти и может различаться между запусками. Она пишется в `workers` и в версии результата.
- Все оценки времени и памяти (≈ 405 визуальных токенов на кадр, 6–6,5 ГБ на 8-bit) — до замеров bench_mac.
- У репозиториев mlx-community нет карточки лицензии: происхождение Apache-2.0 записывается в манифест.
- Путь `video=` и кэширование префикса промпта — только эксперименты, не зависимости.

Что проверяет решение:
- `tests/unit/vlm`: группировка ±2 с, порядок групп, схема ответа.
- `tests/mac`: офлайн-загрузка MLX; ≥ 3 ГБ свободно на ролике 145 с; перекрытие ANE и GPU.
- eval-replay с записанными ответами VLM: LOSO recall 1.0 сохраняется.
