# ADR-0011. Таймкоды по PTS через PyAV и хранилище выбранных кадров на диске

> Назначение: зафиксировать, как считаются таймкоды и откуда берутся кадры-доказательства и кадры для VLM.
> Владелец: S0 (документ, `contracts/video.py`); реализует S3 (`pipeline/decode/pyav_source.py`, `frame_store.py`, `window.py`, `pipeline/evidence/**`). Статус: черновик v1, 17.10.2026.

## Статус

Принято.

## Контекст

- Видео датасета: .mov, H.264, ≈ 29,76–30 fps с переменной частотой кадров (VFR), B-кадры, edit list, moov в конце файла.
- Локализация — 15 баллов. FAQ 17: нужен конкретный кадр и таймкод.
- Кадр-доказательство должен соответствовать таймкоду ([ADR-0006](0006-frozen-jury-contract.md): `evidence_frames[0].timestamp_sec == timecode_sec`).
- VLM работает в отдельном процессе ([ADR-0002](0002-three-process-runtime-supervisor.md)). Без общего хранилища ему пришлось бы декодировать видео заново.
- Финальное видео может быть повёрнуто или в другом кодеке.

## Решение

1. **Декодирование PyAV** (av 19.0.1): `codec_context.thread_type='AUTO'`, программный H.264; VideoToolbox hwaccel — за флагом, выбирается по замеру.
2. **Сетка PTS:** `t = frame.time − start` потока. Декодируется каждый кадр, на сетке выбираются нужные, в BGR конвертируются только они. Применяется `frame.rotation`.
3. **Хранилище кадров:** поток `T-store` пишет каждый выбранный кадр JPEG q85 в `var/jobs/{id}/frames/{pts_ms}.jpg` и индекс `frames/index.json`. Порт `FrameStore`: `put`, `get(t_sec)`, `nearest(t_sec)`, `index()`.
4. **Evidence и кадры VLM — только из хранилища.** Значит `timestamp_sec` всегда равен реальному выбранному PTS. Кадры: событие (`timecode_sec`), увеличенный фрагмент ×3–4, контекст t − 1,5 с.
5. **Срок жизни:** хранилище удаляется после финального результата; `evidence/` остаётся до общей очистки через 24 ч.
6. **Уточнение (опционально, P3):** `decode_window(path, t0, t1, fps)` повторно декодирует окно ±1 с на 10 fps для ≤ 5 кандидатов-переходов.
7. **Длинные видео:** > 300 с — адаптивный fps, чтобы выбранных кадров было ≤ 600.
8. Remux в mp4 для превью — тем же PyAV с `movflags=+faststart`. Системный ffmpeg не нужен.

## Рассмотренные альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Таймкод = `frame_index / fps` | На VFR с edit list время уплывает |
| OpenCV `VideoCapture` | Время кадра опирается на индекс или seek, на VFR с edit list оно уплывает. Второй декодер не нужен, раз PyAV уже есть |
| ffmpeg-подпроцесс с `-vf fps` | Зависимость от системного ffmpeg; пересэмплирование скрывает реальные PTS |
| seek PyAV для кадров-доказательств | Рискованно с B-кадрами и edit list: кадр после seek может не совпасть с нужным PTS |
| Только кольцевой буфер в памяти | Недоступен vlm worker в другом процессе; держит кадры в RAM |

## Последствия

Плюсы:
- Таймкод и кадр-доказательство совпадают по построению.
- VLM не декодирует видео заново.
- Нет системного ffmpeg.

Минусы и цена:
- ≈ 1 с CPU в отдельном потоке и ≈ 30 МБ диска на ролик 145 с (оценка).
- Хранилище нужно чистить: после финального результата и при общей очистке через 24 ч.
- Возможна конкуренция за GIL между потоками декодирования, инференса и записи. Если потери перекрытия > 20 % — декодер в отдельный spawn-процесс с кольцом `shared_memory`.
- На диске лежат кадры камеры: правила deny для агентов (`Read(./var/**)`) и сроки хранения обязательны.

Что проверяет решение:
- Синтетический VFR-фикстур (`tests/fixtures/synthetic_video.py`): таймкоды из PTS.
- Синтетический повёрнутый фикстур: поворот применён.
- Тест: `timestamp_sec` кадра события равен `timecode_sec`.
- `just perf`: декодирование ≤ 6 с на ролик 145 с (оценка).
