# ADR-0005. Уровни дедлайнов от прихода запроса, всегда готовый промежуточный результат и лестница деградации

> Назначение: зафиксировать, как сервис гарантирует ответ жюри за 5 минут при любой нагрузке и сбоях.
> Владелец: S0 (документ, `pipeline/runner.py`); реализуют S1 (`core/budget.py`, `api/sweeper.py`, `jobs/perfstats.py`), S3 (уровни perception), S6 (дедлайны в VLM). Статус: черновик v1, 17.10.2026.

## Статус

Принято. Числа уровней и бюджетов — оценка до замеров `scripts/bench_mac.py` (карточка P0-S6-01 в [roadmap.md](../roadmap.md)); итог пишется в `configs/deadlines.yaml` и `configs/perf_budget.yaml`.

## Контекст

- ТЗ §10 и FAQ 14: если сервис не вернул результат за 5 минут, видео считается необработанным.
- Допущение: часы жюри идут от POST. Значит, в бюджет входит загрузка 29 МБ по каналу жюри.
- Может прийти 5 и больше видео сразу (FAQ 12).
- Оценки на ролик 145 с: perception ≈ 25 с, VLM ≈ 30 с. Пачка из 5 таких роликов без деградации завершается за ≈ 175–190 с (оценка).
- Python-таймауты не прерывают заблокированные вызовы Core ML и Metal.
- Правило из [detection_design.md](../../analysis/detection_design.md) «если в очереди больше одного видео — пропускаем Qwen» грубое: VLM теряется почти на всей пачке, даже когда успевает.
- FAQ 16: пропуск нарушения недопустим. Ответ «только по правилам» с порогом под recall 1.0 лучше, чем отсутствие ответа.

## Решение

1. **Уровни дедлайнов от `t0`** (момент после проверки ключа, до первого байта тела):

   | Уровень | Значение |
   |---|---|
   | `vision_target` | t0 + 150 с |
   | `vlm_start_cutoff` | t0 + 180 с |
   | `vlm_stop` | t0 + 210 с |
   | `finalize_at` | t0 + 225 с |
   | `perception_hard_stop` | t0 + 235 с |
   | ожидаемый худший случай | ≤ t0 + 240 с |
   | аварийный предел (задача уже `done`) | ≤ t0 + 250 с |

   Хранятся в `jobs` как wall-clock epoch (общие для процессов). Внутри процесса бюджет считается по monotonic. Тип `Budget{tiers; now(); remaining(tier); allows(est_sec, tier='vlm_start_cutoff', margin_sec=15)}`.
2. **Промежуточный результат всегда.** Сразу после perception пишутся полные и валидные `analysis.json`, `jury.json`, `ui_result.json` с `result_level=rules`. Только потом CAS ставит `provisional_at`. VLM лишь уточняет этот результат.
3. **Лестница perception.** Уровень `full` (3 fps) → `fast` (1,5 fps) → `min` (1 fps) выбирается на задачу по EWMA из `perf_stats`, длительности, очереди впереди и `vision_target`. Вторая попытка после сбоя — всегда `fast`. Задача, которую воркер взял из очереди позже t0 + 200 с, сразу идёт на уровне `min` с той же жёсткой остановкой (п. 5).
4. **VLM — по условию.** Задача уходит на VLM, только если `CG_VLM_ENABLED`, `now + est_vlm + 15 < vlm_start_cutoff`, свободно ≥ 3,0 ГБ (`CG_MIN_FREE_MEM_GB`; порог совпадает с требованием «≥ 3 ГБ на пике», которое для выпуска проверяет `just perf` в SERVE, [architecture.md, раздел 8](../architecture.md)), очередь vlm помещается и есть кандидаты (или включён keyframe pass). Иначе `done` с `result_level=rules` и причиной деградации.
5. **Кооперативные проверки.** Бюджет проверяется на каждом кадре (perception), на каждой группе и каждом потоковом чанке (VLM, `vlm_stop`). Зависшие процессы убивает supervisor ([ADR-0002](0002-three-process-runtime-supervisor.md)).
   - **Действие при перерасходе perception.** На рубеже `perception_hard_stop` воркер perception прекращает декодирование и прогоняет scene → rules → verdict → evidence по уже обработанным кадрам. Затем пишет промежуточный `jury.json` с деградацией `perception_truncated` и, так как `finalize_at` уже прошёл, сразу выполняет CAS в `done` (`result_level=rules`). Если не успел и он, задачу закрывают sweeper или ленивый GET (п. 6). После t0 + 250 с ни одной задачи в `processing`. Исключение — зависший воркер (`SIGSTOP`, блокирующий вызов): его убивает supervisor, вторая попытка идёт с тем же рубежом; предел для этого случая — 300 с, его проверяет репетиция №1.
6. **Финализация из трёх мест одним идемпотентным CAS** ([ADR-0003](0003-sqlite-wal-queue-state.md)):
   - воркер — при успехе;
   - sweeper в lifespan API — каждые 2 с;
   - ленивый `GET /api/v1/jobs/{id}` — если прошёл `finalize_at` и есть промежуточный результат.
7. **Попытки:** perception — 2 (вторая на `fast`), VLM — 1. Попытки исчерпаны: `done` с промежуточным результатом, если он есть, иначе `failed` (`PIPELINE_CRASH`).
8. **Причины деградации** пишутся в `degradations_json` и видны в UI и `admin/status`: `perception_fast`, `perception_min`, `vlm_deadline`, `vlm_memory`, `vlm_backlog`, `vlm_crash`, `vlm_disabled`, `deadline_finalize`, `perception_truncated`. Тот же список — в перечислении `Degradation` (`contracts/jobs.py`, S0).
9. **Уровень результата:** `full` (VLM проверил всё), `partial` (VLM остановлен до проверки всех групп), `rules` (VLM не запускался или упал). Жюри уровень не видит; в `result_cache` попадает только `full`.

## Рассмотренные альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Один дедлайн 240 с или 270 с от создания задачи | Не учитывает время загрузки. Нет промежуточных точек решения: «успеваем ли начать VLM» |
| Правило «очередь > 1 → пропустить Qwen» | VLM пропадает на большей части пачки, хотя по времени он бы уложился |
| Жёсткие таймауты на SIGALRM или потоках | Не прерывают C-вызовы Metal и Core ML |
| Возвращать `failed` при дедлайне | Видео не засчитывается, хотя ответ по правилам уже есть |

## Последствия

Плюсы:
- Если perception завершился, ответ есть не позже `finalize_at` даже при падении MLX или смерти sweeper. Если perception не успевает, `perception_hard_stop` закрывает задачу не позже t0 + 250 с.
- Результат по правилам — надмножество, безопасное для recall.
- При пачке VLM всё равно проверяет большую часть задач.

Минусы и цена:
- Три пути финализации должны быть строго идемпотентны. Ошибка в CAS-условии даёт гонку.
- Числа — оценки до bench_mac. Если perception не укладывается в `vision_target`, спасают уровень `min` и `perception_hard_stop`; ответ по части кадров слабее по recall, чем полный.
- Если perception падает дважды до промежуточного результата, задача уходит в `failed`. Это единственный путь потери видео после 200, и его нужно держать в фокусе тестов.
- Жюри не видит, что результат неполный: это видно только в UI (бейдж деградации).

Что проверяет решение:
- `tests/api`: ленивая финализация; `tests/workers`: `kill -9` посреди задачи → done; падение VLM → отдан промежуточный результат; perception искусственно замедлена (sleep на кадр) → `done` ≤ 250 с от t0, `result_level=rules`, деградация `perception_truncated` (карточка P2-S1-01).
- `just perf` [macos]: p95 этапов в пределах бюджета +20 %, ≥ 3 ГБ свободно.
- `just jury-sim URL KEY 5`: все done ≤ 240 с от своего POST, ноль 5xx, схема валидна; затем N=10 (≥ 3 ролика по 145 с): каждая задача done ≤ 300 с от своего POST (цель ≤ 270 с), ноль 5xx.
