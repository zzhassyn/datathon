# Анализ кейса ForteBank — Datathon 26

**Задача:** локальный AI-сервис (веб-интерфейс + API), который по видео из кассы выдаёт вердикт `violation` / `no_violation`, а для каждого нарушения — тип, таймкод, 1–3 кадра-доказательства, описание и ссылку на норматив РК.

Источники: `Кейс_ForteBank.docx` (ТЗ + FAQ) и `open.zip` (42 ролика + `open_labels.xlsx`). Типы нарушений организаторы не дали — каталог ниже собран вручную по кадрам. Каждое нарушение сверено с парным «чистым» роликом.

---

## 1. Как оценивают и что из этого следует

| Критерий | Баллы | Вывод для решения |
|---|---|---|
| Обнаружение (вердикт на всё видео) | 25 | Главная метрика. Пропуск «недопустим», ложных срабатываний — «как можно меньше». Порог подбираем под recall ≈ 1, точность добираем верификацией. |
| Локализация (таймкод + кадр) | 15 | «Нужен конкретный кадр и таймкод», допуск не назван. Отдаём кадр, на котором нарушение *видно*, а не начало эпизода. |
| Классификация типа | 15 | Оценка автоматическая, а поле `type` — свободный текст. Нужны стабильные и однозначные названия типов. Скорее всего, их будут сопоставлять с внутренним списком жюри. |
| Обоснованность правил | 15 | Только акты РК (НБРК, adilet). За выдуманные пункты штрафуют. Ссылки без точного пункта допускаются (FAQ 31). |
| Устойчивость | 10 | Финальное видео снимут **под другим углом**. Хардкодить зоны в пикселях нельзя. |
| Готовность продукта | 10 | Загрузка .mov ~29 МБ, статус обработки, понятный результат. |
| Техническое решение | 10 | Локальность (за облачные API — дисквалификация), лицензии моделей должны разрешать коммерческое использование. |

API асинхронный: `POST /api/v1/analyze` → `job_id`, затем `GET /api/v1/jobs/{id}`. Ключ передаётся в `X-API-Key`. Лимит — **5 минут на видео**, иначе ролик считается необработанным. Вердикта «недостаточно данных» в схеме нет, поэтому выбираем строго из двух.

## 2. Датасет: факты и ловушки

- **42 строки разметки, но 40 уникальных роликов.** `Х-4` и `Х-47` совпадают байт-в-байт (MD5), как и `Х-5` с `Х-48`. При этом `Х-4` размечен на 57 с, а `Х-47` — на 68 с. Это один ролик с двумя нарушениями: формат разметки допускает только один таймкод на строку, поэтому файл продублировали.
- **Смешанные алфавиты в именах:** `X-1`, `X-2` начинаются с латинской X, остальные — с кириллической Х. Без нормализации join с разметкой молча теряет строки.
- **Формат таймкода — текст:** `"22 секунда"`, `"1минута 8 секунда"`.
- **Видео:** 464×848 (портрет), ~30 fps, H.264, без звука, 11,6–142,5 с.
- **Баланс:** 21 ролик с нарушением (22 события) и 19 чистых.
- **Конфаундер длительности.** Медиана роликов с нарушением — 20 с, чистых — 26 с. Среди роликов ≤ 26 с нарушения есть в 18 из 21, а среди чистых — в 9 из 19. Модель, которая учит видео целиком, может выучить длительность вместо нарушения.
- **Ролики снимали парами:** один сценарий записан правильно и с нарушением (`Х-12`/`Х-11`, `Х-23`/`Х-22`, `Х-16`/`Х-17` …). Это лучший учебный сигнал: разница пары и есть нарушение. Но при случайном train/val-сплите пары утекают, поэтому делить нужно по сценариям (group split).
- **Таймкод в разметке означает разное.** Иногда это причина (`Х-32`, `Х-33`: момент, когда кассир не закрыла дверь), иногда следствие (`Х-30`: момент, когда вошёл посторонний). Нарушения в среднем начинаются на 13-й секунде, около 2/3 длины ролика.
- **5 сцен (ракурсов)** в одной комнате: стол, ноутбук, счётная машинка, детектор подлинности, сейф, стеклянная дверь. Кассир в розовом или белом. Клиенты и инкассаторы входят через дверь. Освещение иногда выключают (`Х-11`, `Х-12`).

Что из этого следует:
1. **Почти все нарушения — это пропущенный обязательный шаг или неверное состояние объекта** (сейф открыт, экран не заблокирован, дверь не закрыта, удостоверение не показано). Классификатор действий на 40 роликах это не выучит. Нужна логика «процедура → обязательные шаги → проверка, был ли шаг», поверх детекции объектов и людей.
2. **Ключевые признаки мелкие:** ключ в замке, экран блокировки, детектор подлинности. Нужен анализ кропов в высоком разрешении вокруг найденных объектов, а не кадра целиком 464×848.
3. **В тесте будут новые типы** (FAQ 9). Нужен общий проход, который ловит подозрительное за пределами списка правил. Подходит локальная VLM по ключевым кадрам.

## 4. Рекомендуемая архитектура

```
.mov ─► декодирование 2–4 fps ─► калибровка сцены (первые кадры):
        open-vocab детектор находит дверь, сейф, стол, ноутбук, машинку, детектор
        → зоны в координатах кадра (работает для нового ракурса)
     ─► трекинг людей (без распознавания лиц — FAQ 29) + роли по поведению:
        кассир = сидит со «служебной» стороны стола / открывает сейф;
        вошедший через дверь = клиент / инкассатор (сумка) / посторонний
     ─► состояния объектов по времени (кропы ROI): сейф открыт/закрыт, ключ в замке,
        экран ноутбука (рабочий/блокировка/выкл), дверь открыта, деньги/сумка на столе
     ─► движок правил (конечные автоматы по процедурам) → кандидаты событий
        (тип, t, кадры, уверенность)
     ─► верификация кандидатов локальной VLM (вопрос да/нет по 3–6 кадрам)
        + общий VLM-проход «что необычного» для неизвестных типов
     ─► вердикт (порог под recall), таймкод = кадр, где нарушение видно,
        кадр-доказательство с рамкой, описание по шаблону + ссылка на норматив
```

**Модели.** Выбирать только с коммерческими лицензиями (FAQ 24). Право на решение получает банк (FAQ 34). Лицензии ниже взяты из карточек Hugging Face и данных GitHub на 17.10.2026.

| Роль | Модель | Лицензия | Обучать? |
|---|---|---|---|
| Понимание видео, верификация, описание | **Qwen3.5-4B** — MLX 8-bit, 5,1 ГБ, VideoMME 76,9; на MacBook M2 Pro 16 ГБ оставляет 3–4 ГБ свободными. Запасной вариант — 4-bit, 3,0 ГБ. Qwen3.5-9B (78,4) не оставляет запаса памяти; Qwen3-VL-4B слабее (69,3) | Apache-2.0 | Нет, zero-shot. LoRA — только при наличии своей съёмки |
| Детекция людей и предметов | **YOLO26** (Ultralytics; разрешено организаторами); запасной вариант — RF-DETR / D-FINE | AGPL-3.0; запасной вариант — Apache-2.0 | **Да — главный обучаемый компонент** |
| Пред-разметка кадров | Grounding DINO, OWLv2, Florence-2 | Apache-2.0 / MIT | Нет |
| Состояния по кропам (сейф, ключ, экран, дверь) | SigLIP2 или DINOv2 + линейный классификатор | Apache-2.0 | **Да, few-shot linear probe** |
| Трекинг, поза рук | ByteTrack; RTMPose (MMPose) | MIT; Apache-2.0 | Нет |

**С условиями:**
- Ultralytics YOLO (v5/v8/11/26) — двойная лицензия: AGPL-3.0 или платная Enterprise.
  - **Организаторы подтвердили, что YOLO использовать можно (17.10.2026).** Сохраните скриншот ответа и сошлитесь на него в README.
  - **Правилам хакатона AGPL-3.0 не противоречит**: коммерческое использование она не запрещает.
  - Но наш сервис работает по сети (публичный API). По позиции Ultralytics AGPL требует открыть исходники **всего проекта**: код, конфиги, скрипты обучения, при необходимости веса. Иначе нужна Enterprise-лицензия, причём даже для внутреннего использования и модели, обученной с нуля.
  - Банк получает право на коммерческое использование решения (FAQ 34) и будет разворачивать его во внутреннем контуре. Значит, ему придётся либо открыть код, либо покупать лицензию у Ultralytics.
  - Если берёте YOLO — опубликуйте код сервиса под AGPL и укажите это ограничение в README.
- YOLOv10 — тоже AGPL-3.0. YOLOv6/v7/v9 — GPL-3.0.

**Не брать:**
- VideoMAE — веса CC-BY-NC, некоммерческие.
- Qwen2.5-VL-3B — qwen-research.
- Qwen3.8-Flash-Next — qwen-community-1.0, без юридической проверки.
- DINOv3, SAM 3 — собственные лицензии с доступом по запросу; только после проверки.

**Бюджет.** 145 с × 3 fps ≈ 435 кадров на детектор + общий VLM-проход ≈ 1 fps + 5–10 коротких окон на верификацию. Ориентировочно укладывается в 5 минут на одной GPU 24–48 ГБ, это стоит проверить замером. Режим thinking у Qwen3.5 отключать ради скорости. Без GPU VLM-этап придётся урезать до нескольких кропов на маленькой модели.

**Описание для проверяющего** строим по шаблону из фактов пайплайна («в 14,0 с кассир покидает кассу; в замке сейфа остаётся ключ»). Свободная генерация VLM не годится: ТЗ требует «без неподтверждённых предположений», и за выдумки снимают баллы.

## 5. План работ (по ценности для баллов)

1. **Каркас продукта первым делом:** FastAPI + очередь задач + JSON строго по схеме + ключ + простой веб-интерфейс + публичный URL. Без этого 0 баллов по всем критериям.
2. **Инфраструктура данных:** нормализация имён, парсер таймкодов, дедупликация, typed labels, group split по парам, скрипт оценки (вердикт, |Δt|, тип).
3. **Самые частые и надёжно видимые типы:** уход с рабочего места (4 подтипа, 7 роликов) и доступ в кассу (5 подтипов, 7 роликов). Это две трети событий.
4. Процедурные типы (ID, инкассатор, пересчёт), затем VLM-верификатор и общий проход.
5. **Своя съёмка с других ракурсов** (FAQ 7 разрешает). Это прямая подготовка к финальному видео с другим углом.
6. Нормативная таблица «тип → акт → пункт → формулировка». Ссылки только проверенные.

## 6. Риски

- Финальный ракурс другой. Зоны в пикселях сломаются, поэтому нужна авто-калибровка и проверка на всех 5 сценах с leave-one-scene-out.
- Неизвестные типы в тесте. Без общего прохода их пропустим, а пропуск хуже ложной тревоги.
- Ложные срабатывания на чистых роликах вроде Х-8, Х-10, Х-43, Х-45: обычная работа с деньгами похожа на нарушение.
- Двусмысленная разметка: Х-1 и Х-44 трактуются со средней уверенностью, таймкоды то причина, то следствие.
- Лицензии моделей и локальность. Облачные вызовы при обработке, включая отправку описаний кадров, ведут к дисквалификации.
- Данные хакатона нельзя публиковать и хранить после него. Видео в git не коммитить.

### Соответствие «тип нарушения → норма»

**Прямая** — норма описывает именно это действие. **Косвенная** — норма задаёт требование, из которого нарушение следует по трактовке. Для косвенных в описании пишем «может свидетельствовать о несоблюдении требования…», а не «нарушен пункт».

| Тип | Норма | Ключевая формулировка | Сила |
|---|---|---|---|
| Приём наличных без документа клиента (Х-2) | ПКО п.19 пп.1); при выдаче — п.31 пп.1) | «проводит визуальную идентификацию клиента, вносящего наличные деньги, с документом, удостоверяющим его личность, либо данными… полученными посредством сервиса цифровых документов» | Прямая. Оговорка: цифровой документ на телефоне тоже допустим |
| Пересчёт не в присутствии клиента (Х-34) | ПКО п.20 ч.1 | «Наличные деньги принимаются и пересчитываются кассовым работником в присутствии клиента.» | Прямая |
| Неполная выдача / утаивание (Х-1) | ПКО п.31 пп.4); п.35; п.14 | «пересчитывает подготовленные к выдаче наличные деньги в присутствии клиента, выдает клиенту наличные деньги» | Прямая к процедуре. Квалифицировать «хищение» сервис не вправе (раздел 7 ТЗ) |

### Чего в актах нет (не выдумывать)
- Отдельного запрета «сейф открыт», «наличные без присмотра», «обслуживать одного клиента за раз». Есть только п.20 ч.2, п.21, п.22 ПКО.
- Общего запрета посторонних в обычной кассе банка. Он есть для кладовой (п.75 ПКО) и для кассы обменного пункта (п.41 ПОО).
- Требования «считать деньги в зоне видимости камеры» для обычной кассы. ПОП п.16 пп.6) требует только наличия камер, а правило про «рабочую зону и клиента в обзоре» есть только для обменного пункта (ПОО п.11 пп.2).
- Обязанности вручную блокировать ПК. ТИБ п.71 пп.9) описывает автоблокировку через 30 минут.

### Подсказки для неизвестных типов в тесте (из тех же актов)
- **Смартфон с камерой у кассира.** ПКО п.12 разрешает вносить в кассовый узел только «средства связи, не имеющих функции фото и видео фиксации». Тип хорошо виден на видео и легко проверяется.
- **Кассир уходит до окончания обслуживания клиента.** ПКО п.22 — прямая норма.
- **Клиент уходит, не пересчитав полученные деньги.** ПКО п.35.
- **Передача денег между кассирами без оформления.** ПКО п.15. Оформление на видео не видно, поэтому это скорее ограничение, чем детектируемый тип.
